# Auto-Memory Protocol

> Claude Code 의 **세션 간 자동 메모리** 를 어떻게 사용할지에 대한 가이드.
> 이 템플릿이 강제하는 게 아니라, 1인 개발자가 효과적으로 굴리기 위한 컨벤션.

---

## 두 종류의 영속성

이 템플릿엔 이미 두 가지 영속 메커니즘이 있다:

| 위치 | 무엇 | 라이프타임 |
|------|------|-----------|
| `.work/snapshots/` | PreCompact hook 이 압축 직전 자동 저장하는 작업 상태 스냅샷 | 한 세션 ~ 며칠 |
| `.work/MISTAKES.md` | 사람이 직접 추가하는 오답 노트 (append-only) | 영구 |

여기에 **세 번째** 가 있다:

| 위치 | 무엇 | 라이프타임 |
|------|------|-----------|
| `~/.claude/projects/<project-slug>/memory/` | Claude Code 가 자동으로 읽고 쓰는 사용자/프로젝트 메모리 | 영구 (대화 간 유지) |

이 디렉토리는 Claude Code 가 **새 대화가 시작될 때마다** `MEMORY.md` 인덱스를
자동으로 컨텍스트에 로드한다. 사용자가 매번 "지난번에 우리가 정한 게…" 를
설명할 필요가 없다.

---

## 메모리의 4가지 유형

Claude 가 메모리를 저장할 때는 다음 네 유형 중 하나로 분류한다.

| 유형 | 무엇을 담나 | 언제 저장하나 | 예시 |
|------|------------|---------------|------|
| **user** | 사용자의 역할/배경/선호 | 사용자의 정체성을 알게 됐을 때 | "10년차 Go 개발자, React 는 처음" |
| **feedback** | 사용자가 준 작업 가이드 (정정 + 검증된 판단 둘 다) | 사용자가 "그렇게 하지 말고…" 또는 "그래 그게 맞아" 라고 했을 때 | "DB 테스트는 mock 금지 — 작년 마이그레이션 사고 때문" |
| **project** | 진행 중인 작업/목표/마감/이해관계자 | 코드만 봐선 알 수 없는 동기·맥락을 알게 됐을 때 | "auth 미들웨어 재작성은 컴플라이언스 요구사항 때문" |
| **reference** | 외부 시스템 위치 포인터 | 대시보드/티켓트래커/문서 위치를 알게 됐을 때 | "파이프라인 버그는 Linear INGEST 프로젝트에서 추적" |

> **저장하지 말 것**: 코드 패턴/아키텍처/파일 경로 — 이건 코드를 읽으면 안다.
> Git history 도 마찬가지. 메모리는 *코드/git 으로 복원 불가능한* 정보만.

## 파일 구조

```
~/.claude/projects/<your-project-slug>/memory/
├── MEMORY.md                       # 인덱스 (한 줄/엔트리, ~150자, 항상 로드됨)
├── user_profile.md
├── feedback_collaboration.md
├── feedback_testing.md
├── project_current_milestone.md
└── reference_dashboards.md
```

각 메모리 파일은 frontmatter 가 있다:

```markdown
---
name: {짧은 이름}
description: {한 줄 — 미래의 Claude 가 "이게 지금 관련 있나?" 판단할 단서}
type: user | feedback | project | reference
---

{본문 — feedback/project 는 "규칙/사실" 다음에 **Why:** 와 **How to apply:** 줄 권장}
```

`MEMORY.md` 인덱스는 본문이 아니라 **포인터** 만 담는다:

```markdown
- [User profile](user_profile.md) — Go senior, React 입문, founder
- [Testing rules](feedback_testing.md) — DB 테스트 mock 금지 (사고 기반)
- [Current milestone](project_current_milestone.md) — Phase 1, 2026-06-01 마감
```

## 운영 규칙

### 사용자가 명시적으로 부탁하면 즉시 저장
"이거 기억해 줘" → 4 유형 중 가장 맞는 곳에 저장.
"이거 잊어 줘" → 해당 엔트리 찾아 삭제.

### 조용한 신호도 잡기
정정(`"그렇게 하지 말고"`)은 눈에 띄지만, **검증**(`"좋아 그게 맞았어"`)도
똑같이 중요하다. 후자가 빠지면 메모리는 "하지 말 것" 만 쌓여 점점 보수적이 된다.

### Why 를 적기
규칙만 적고 이유를 빼면, 미래의 Claude 가 엣지 케이스를 판단할 수 없다.
"X 하지 말 것" + "**Why:** 작년 Y 사고" + "**How to apply:** Z 영역에서만" 패턴.

### 시간 표현은 절대 날짜로
"목요일까지" → `2026-04-09`. 메모리는 영구이므로 상대 시간은 곧 의미를 잃는다.

### 메모리는 진실의 스냅샷, 코드가 권위
메모리에 "함수 X 가 파일 Y 에 있다" 라고 적혀 있어도, 추천하기 전에 grep 으로
확인. 메모리는 *그 시점에 그랬다* 의 기록이지 *지금도 그렇다* 의 보장이 아니다.

### 중복 회피
새 메모리를 쓰기 전에 기존 인덱스를 보고, 업데이트로 충분하면 업데이트한다.

## 다른 영속 메커니즘과의 분담

세 가지 모두 "오래 가는 정보" 를 다루지만 역할이 다르다:

| 정보 | 어디에 | 이유 |
|------|--------|------|
| 현재 세션 진행 상황·다음 할 일 | `PLAN.md`, 또는 대화 내 task | 세션 내 단기 |
| 컨텍스트 압축 직전의 작업 상태 | `.work/snapshots/` (자동) | 세션 회복용 단기 |
| 한 번 발생한 실수의 교훈 | `.work/MISTAKES.md` (수동, append-only) | 레포 단위, 사람이 읽음 |
| 사용자의 선호·역할·동기·외부 포인터 | `~/.claude/projects/<slug>/memory/` (자동) | 대화 간 영구, Claude 가 자동 로드 |

원칙: **현재 대화 안에서만 쓸모 있는 건 메모리에 넣지 않는다.** plan/task 로
충분하다.

## 시작하기

1. 새 프로젝트라면 처음 몇 세션 동안은 메모리가 비어 있는 게 정상이다.
2. 사용자가 자기 배경, 작업 방식, 우선순위를 자연스럽게 흘릴 때 Claude 가
   하나씩 저장한다.
3. 한 달쯤 지나면 `MEMORY.md` 인덱스가 10~20 줄 정도로 안정화된다.
4. 인덱스가 그 이상 부풀면 통합/삭제할 시점이다 (Claude Code 는 첫 200 줄만
   로드한다).

> 이 가이드 자체는 **강제 hook 이 아니다**. 가이드 문서일 뿐.
> Claude Code 의 자동 메모리 동작을 어떻게 활용할지에 대한 컨벤션이다.
