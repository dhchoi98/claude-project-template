# Checklists

> 작업 전후에 빠르게 훑는 체크리스트 모음.

---

## 1. 새 프로젝트 시작

```
[] setup.sh로 초기화 (--type, --rigor, --mode 선택)
[] CLAUDE.md 기술스택 테이블 채우기
[] CLAUDE.md 용어 테이블에 도메인 용어 추가
[] PLAN.md에 Phase 1 태스크 작성
[] .env.example 생성 (필요한 환경변수 목록)
[] .gitignore에 프로젝트 특화 항목 추가
[] init-labels.sh로 GitHub 라벨 생성
[] setup.sh, init-labels.sh 삭제
[] 첫 커밋
```

---

## 2. 새 기능 추가

```
[] contracts.py에 인터페이스가 필요한가? -> 필요하면 직접 추가
[] feature 브랜치 생성
[] AI에게 테스트 생성 요청 (계약 기반)
[] AI에게 구현 요청 (파일 위치, 타입, 로직 명시)
[] 리뷰: 타입 힌트, 하드코딩, 에러 핸들링
[] 로컬 검증: pytest + mypy (또는 해당 언어 도구)
[] 커밋 (conventional commits)
[] PLAN.md 업데이트
```

---

## 3. AI 코드 리뷰

AI가 코드를 생성한 후 확인:

```
[] 타입 힌트가 빠진 곳 없는가?
[] .env나 secrets가 하드코딩되지 않았는가?
[] 기존 core/ 코드를 수정하지 않았는가? (확장만 했는가?)
[] import 경로가 맞는가?
[] 에러 핸들링이 있는가? (특히 외부 API 호출)
[] 로깅이 적절한가? (print 대신 logging)
[] 파일 상단 docstring이 있는가?
[] 불필요한 코드가 추가되지 않았는가? (오버엔지니어링)
```

---

## 4. 커밋 전

```
[] 테스트 통과 (pytest / vitest / go test)
[] 타입 체크 통과 (mypy / tsc / go vet)
[] 린트 통과 (ruff / biome / gofmt)
[] .env 파일이 커밋에 포함되지 않았는가?
[] 민감한 데이터가 노출되지 않았는가?
```

> 이 중 대부분은 `.claude/hooks/pre-commit.sh`가 자동으로 잡아준다.

---

## 5. 멀티세션 티켓 설계 (team 모드)

```
[] 각 티켓의 파일 범위가 겹치지 않는가?
[] 공유 파일(설정, 타입 정의)을 동시에 수정하는 티켓이 없는가?
[] 의존성이 있는 티켓은 순서가 보장되는가?
[] 각 티켓이 독립적으로 테스트 가능한가?
[] CC/Auto/Premium 도구 배정이 적절한가?
```

---

## 6. Anti-patterns — 절대 하지 말 것

| Anti-pattern | 왜 위험한가 | 대안 |
|---|---|---|
| `from module import *` | 네임스페이스 오염, AI가 출처를 모름 | 명시적 import |
| 글로벌 변수 변경 | 사이드이펙트, 디버깅 불가 | 함수 파라미터로 전달 |
| `Any` 타입 남발 | AI가 추측하게 만듦 | 구체적 타입 명시 |
| `print()` 디버깅 | 프로덕션에 남으면 문제 | `logging` 모듈 |
| `.env` 커밋 | 시크릿 노출 | `.env.example`만 커밋 |
| `try: ... except: pass` | 에러 삼킴, 원인 추적 불가 | 구체적 예외 + 로깅 |
| 한 파일에 500줄+ | 리뷰 불가, AI 컨텍스트 초과 | 모듈 분리 (200줄 이하 목표) |
| 테스트 없이 리팩토링 | 깨뜨려도 모름 | 테스트 먼저, 리팩토링은 나중 |
| "나중에 고치지" 주석 | 영원히 안 고침 | TODO + 이슈 등록 |
| 완벽주의 | 아무것도 릴리즈 안 됨 | "Done is better than perfect" |
| AI에게 모호하게 지시 | 추측 -> 버그 | 파일/타입/로직 전부 명시 |
| contracts.py를 AI에게 수정시킴 | 아키텍처 흔들림 | 사람만 수정 |
