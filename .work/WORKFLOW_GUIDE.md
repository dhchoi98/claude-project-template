## 0. Solo 모드 (1인 개발)

`setup.sh --mode solo`로 설정 시 사용. 5세션 프로토콜 없이 간결하게 작업한다.

```
1. PLAN.md에서 할 일 확인
2. (선택) Plan 모드로 계획 수립
3. 구현
4. 자가 검증
5. PLAN.md 업데이트
```

- 티켓/BOARD/핸드오프 불필요
- .work/ 디렉토리는 오답노트(MISTAKES.md)와 ADR만 활용
- 나머지 아래 내용은 **team 모드**에 해당

## 1. 기본 개념 (Team 모드)

```
당신 = 수석 개발자 (아키텍트 + PM)
세션 1~5 = 팀원 5명 (각각 독립 티켓 수행)
BOARD.md = 칸반 보드
핸드오프 = 퇴근 시 인수인계
```

### 핵심 원칙
- **티켓 단위 분배**: 역할 고정(프론트 전담, 백엔드 전담)이 아니라, 독립적인 티켓을 유동적으로 배분
- **Plan 후 실행**: 모든 세션은 Plan 모드로 시작 → 계획 합의 → auto-accept로 구현
- **파일 범위 격리**: 티켓마다 건드리는 파일이 겹치지 않도록 설계
- **자가 검증**: 코드 작성 후 스스로 테스트/빌드 검증

## 2. 시작하기: 사전 준비

### Step 1: 티켓 설계 (가장 중요)

BOARD.md에 티켓을 등록하기 전에 **파일 범위가 겹치지 않도록** 쪼갠다.

```
예시: "사용자 인증 기능" → 5개 독립 티켓으로 분해

T001  User 모델 정의         → src/models/user.*
T002  인증 API 엔드포인트     → src/api/auth.*, src/services/auth.*
T003  로그인/회원가입 UI      → src/pages/auth/*, src/components/auth/*
T004  인증 미들웨어 & 가드    → src/middleware/auth.*, src/guards/*
T005  인증 테스트 스위트       → tests/auth/*
```

### Step 2: BOARD.md에 등록

티켓을 BOARD.md의 티켓 큐에 추가한다. 반드시 `파일 범위`를 명시한다.

### Step 3: 터미널 탭 5개 열기

```
탭 1: claude  → /start → /claim T001
탭 2: claude  → /start → /claim T002
탭 3: claude  → /start → /claim T003
탭 4: claude  → /start → /claim T004
탭 5: claude  → /start → /claim T005
```

## 3. 각 세션에서의 작업 흐름

### 세션 시작
```
/start              ← BOARD, 핸드오프, PLAN 자동 읽기
/claim T{XXX}       ← 티켓 클레임
```

### 계획 수립 (Plan 모드)
세션에게 지시:
```
"T001 — User 모델 정의를 구현해줘.
 Plan 모드에서 계획을 먼저 보여줘."
```
- 세션이 계획을 제시하면 검토 후 승인
- 승인 후 auto-accept로 구현 진행

### 구현 중 모니터링
- 5개 탭을 순회하며 진행 상황 확인
- 질문이 오면 답변, 방향 수정이 필요하면 개입

### 작업 완료
```
/review             ← 변경사항 자가 리뷰
/end                ← 핸드오프 작성 + BOARD 업데이트
```

### Git 작업 (사용자가 직접)
- 세션이 끝난 후 사용자가 직접 커밋/푸시를 결정
- 또는 특정 세션에 Git 작업을 지시

## 5. 충돌 방지 체크리스트

티켓을 세션에 배분하기 전 확인:

- [ ] 각 티켓의 파일 범위가 겹치지 않는가?
- [ ] 공유 파일(설정, 타입 정의 등)을 동시에 수정하는 티켓이 없는가?
- [ ] 의존성이 있는 티켓은 순서가 보장되는가? (선행 티켓이 먼저)
- [ ] 각 티켓이 독립적으로 테스트 가능한가?

### 공유 파일 충돌 해결 전략

```
방법 1: 순차 처리
  → 공유 파일을 수정하는 티켓은 한 세션에 몰아주고 나머지는 다른 작업

방법 2: 인터페이스 먼저
  → 세션 1이 공유 인터페이스/타입을 먼저 정의 (T001)
  → 나머지 세션은 T001 완료 후 구현 시작 (T001 의존)

방법 3: 로컬 스텁
  → 각 세션이 자기 범위에서 스텁/목을 사용
  → 마지막에 통합 세션에서 연결
```

## 6. 백그라운드 & 서브 태스크 (--teleport)

> 로컬 터미널 5개가 주 작업 세션이라면,
> `--teleport`로 넘긴 웹 세션은 비동기 백그라운드 워커다.

### 전체 구조

```
┌─ 로컬 터미널 (탭 1~5) ─────────────────────┐
│  S1~S5: 핵심 개발 티켓 (대화형, Plan→구현)    │
└─────────────┬───────────────────────────────┘
              │ --teleport (브라우저로 전환)
              ▼
┌─ 웹 세션 (5~10개 추가) ────────────────────┐
│  B1~B10: 장시간 백그라운드 태스크              │
│  코드 분석, 문서화, 테스트 생성, 리뷰 등       │
└─────────────────────────────────────────────┘
```

### --teleport 사용법

```bash
# 방법 1: 진행중인 로컬 세션을 웹으로 넘기기
# 로컬 세션에서 시간이 오래 걸리는 작업이 시작되면:
claude --teleport
# → 브라우저에서 해당 세션이 계속 실행됨
# → 로컬 터미널은 즉시 해방 → 다른 티켓에 사용

# 방법 2: 처음부터 백그라운드 태스크로 시작
claude --teleport -p "src/ 전체를 분석해서 docs/architecture.md를 작성해줘"
# → 브라우저에서 바로 실행, 로컬 터미널 점유 안 함

# 방법 3: 여러 백그라운드 태스크 동시 실행
claude --teleport -p "tests/ 커버리지 분석 후 누락된 테스트 목록 작성"
claude --teleport -p "모든 API 엔드포인트 문서화해서 docs/api.md 작성"
claude --teleport -p "의존성 보안 취약점 체크 후 리포트 작성"
# → 3개가 브라우저 탭에서 동시에 돌아감
```

### 로컬 세션 vs 웹 백그라운드 기준

| 기준 | 로컬 세션 (탭 1~5) | 웹 백그라운드 (--teleport) |
|------|-------------------|--------------------------|
| 대화형 여부 | 계획 수립, 실시간 피드백 필요 | 단방향 지시, 결과만 확인 |
| 소요 시간 | 짧음~중간 | 장시간 |
| 개입 빈도 | 자주 확인, 방향 수정 | 완료 후 한 번 확인 |
| 예시 | 기능 구현, 버그 수정 | 코드 분석, 문서화, 대량 테스트 |

### 백그라운드에 적합한 작업

- 대규모 코드베이스 분석 & 아키텍처 문서 생성
- API 문서 자동 생성
- 테스트 커버리지 분석 & 누락 테스트 목록
- 의존성 업데이트 검토 & 보안 체크
- 코드 스타일 일괄 적용
- 크로스 리뷰 (다른 세션이 작성한 코드 리뷰)
- 레거시 코드 분석 & 리팩토링 계획 수립

### BOARD.md 연동

백그라운드 티켓도 BOARD.md에 등록한다. 도구 컬럼에 `BG`를 사용:

```markdown
| ID | 티켓 | 유형 | 도구 | 상태 | 담당 | 파일 범위 | 의존성 |
|----|------|------|------|------|------|----------|--------|
| T010 | 아키텍처 문서 생성 | docs | BG | [~web] | — | docs/architecture.md | — |
| T011 | 테스트 커버리지 분석 | test | BG | [~web] | — | docs/coverage.md | — |
```

### 실전 워크플로우 예시

```
09:00  로컬 5탭 시작
       S1: T001 CC    "인증 아키텍처 설계"
       S2: T002 CC    "DB 스키마 설계"
       S3: T003 Auto  "결제 API 구현"        ← Cursor Auto (무제한)
       S4: T004 Auto  "사용자 프로필 구현"     ← Cursor Auto (무제한)
       S5: T005 Auto  "유틸 함수 테스트"       ← Cursor Auto (무제한)

09:10  백그라운드 3개 teleport
       claude --teleport -p "전체 코드베이스 의존성 분석"
       claude --teleport -p "기존 API 문서 최신화"
       claude --teleport -p "보안 취약점 스캔"

10:00  S1 설계 완료 → /end → 핸드오프 작성
       S1에 새 티켓 할당: T006 Auto "로그인 API 구현"

       백그라운드 결과 확인 → 필요시 후속 티켓 생성
```

## 7. 리뷰 및 검증 루프

### 크로스 리뷰
세션 A의 작업이 끝나면, 세션 B에게 리뷰를 지시:
```
"방금 S1이 src/models/user.* 에서 작업을 완료했어.
 .work/handoffs/ 에서 S1의 핸드오프를 읽고,
 해당 코드를 리뷰해줘. 보안, 성능, 가독성 관점에서."
```

### 통합 검증
모든 세션 작업 후:
```
"모든 세션 작업이 끝났어.
 전체 테스트를 실행하고,
 빌드가 성공하는지 확인해줘."
```
