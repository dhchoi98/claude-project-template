## 티켓 설계 규칙

### 유형
- `feat` — 새 기능 개발
- `fix` — 버그 수정
- `refactor` — 리팩토링
- `test` — 테스트 작성
- `docs` — 문서화
- `chore` — 설정/빌드/인프라

### 도구 배정 기준

| 도구 | 역할 | 적합한 작업 | 비용 |
|------|------|------------|------|
| `CC` | 수석 아키텍트 | 아키텍처 설계, 디자인 패턴 적용, 멀티파일 구조 변경, 복잡한 버그 추적, 스켈레톤/인터페이스 생성 | 높음 |
| `DS` | 시공반장 A | 구현체 채우기, 비즈니스 로직 구현, API 엔드포인트, 리팩토링, 복잡한 단위 코드 작성 | 낮음 |
| `Kimi` | 시공반장 B | 테스트 양산, 문서/주석 보강, 타입/보일러플레이트, 스타일 수정, 반복적 코드 생성 | 낮음 |
| `Any` | — | 어느 도구든 상관없는 작업 | — |

**일반적인 흐름:**
```
CC (설계) → DS (구현) → Kimi (테스트/문서)

  T001 CC   "인증 아키텍처 설계"     → T002 DS   "로그인 API 구현"     → T003 Kimi "인증 테스트 스위트"
  T004 CC   "DB 스키마 & 모델 설계"  → T005 DS   "CRUD 구현체 작성"   → T006 Kimi "모델 테스트 & 문서"
```

### 좋은 티켓의 조건
1. **독립적**: 다른 티켓과 파일 범위가 겹치지 않는다
2. **명확한 범위**: 파일 범위 컬럼에 구체적인 파일/디렉토리가 명시된다
3. **검증 가능**: 완료 기준이 명확하다 (테스트 통과, 빌드 성공 등)
4. **적절한 크기**: 한 세션에서 완료할 수 있는 크기

### 충돌 방지를 위한 티켓 쪼개기 예시
```
❌ 나쁜 예: T001 "사용자 기능 전체 구현" (범위 너무 넓음)

✅ 좋은 예 (CC→DS→Kimi 파이프라인):
  T001 CC   "User 모델 & 인증 아키텍처 설계"   파일: src/models/user.*, docs/auth.md
  T002 DS   "회원가입 API 구현"                파일: src/api/auth.*
  T003 DS   "회원가입 UI 폼"                   파일: src/pages/signup.*
  T004 Kimi "회원가입 테스트"                   파일: tests/auth/*
  T005 Kimi "인증 API 문서"                    파일: docs/api/auth.*
  T006 CC   "인증 미들웨어 & 보안 검토"          파일: src/middleware/auth.*
```

### 보드 조작
1. **클레임**: `[ ]` → `[~S{N}]` + 담당에 세션 번호
2. **완료**: `[~S{N}]` → `[x]` + 완료 이력에 추가
3. **블로커**: `[!]` + 사유 기록
4. **의존성**: 선행 티켓이 `[x]`가 아니면 클레임 불가
